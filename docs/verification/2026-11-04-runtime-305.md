## Linux harness correction

The first Linux arm64 matrix attempt exposed a test-harness defect: Node's
Linux task name is `MainThread`, so identifying its executable from `ps comm`
missed the child adapter after successful attachment. The attempt failed at
the unchanged 240-second PID-discovery bound; it is retained as a failure.

The harness now resolves Linux executable identity through `/proc`, including
the guest executable when running through QEMU's binfmt interpreter. Process
exposure checks use that same identity and require the actual adapter to appear
in the evidence. Raw command arguments remain private to the inspection helper.

A regression starts a real shell, renames its Linux task to `MainThread`, and
checks its executable identity. It failed before the fix (exit 101, one failed
test) and passed afterwards (exit 0, one passed test). The complete harness unit
checks passed on Linux arm64 (8 passed, 10 opt-in tests ignored) and macOS
(7 passed, 10 ignored). Both actual macOS adapter/process probes also passed
again after the correction. Provider prompts, lifecycle assertions and timeout
bounds were unchanged.

## Linux qualification

Linux acceptance runs in disposable containers inside a separate Linux VM,
without mounting the operator's home or application data. Arm64 executes
natively; x64 executes through QEMU binfmt emulation. Both use the candidate's
platform-specific Node, adapters and native CLIs from the production installer.

The candidate's current Linux results, per-platform counts and outstanding gates
are recorded in [PR #305](https://github.com/marcinwadon/hennery/pull/305).
Emulated x64 provider tests and native GitHub Actions packaging/installation
checks are separate evidence; emulation establishes no native performance claim.
