# Passkeys (plan 3c) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ] `) syntax for tracking.

**Goal:** The owner can register passkeys, sign in with one, and step up with one (kernel spec §3.2, §3.4; umbrella §7.3):
- WebAuthn through `webauthn-rs`, with the relying party taken from `public_url`: its host is the RP id, its origin the one origin accepted.
- Several labelled passkeys per owner, listed with their last use, registered and removed only from a stepped-up session. The password stays.
- Login and step-up by passkey, each opening or stepping up a session in one transaction with the passkey's counter, and refused when the counter goes back.
- Ceremony state in memory: single use, five minutes, bound to its session.
- `hennery admin reset-public-url` says that passkeys stop working, and removes those bound to a host name it no longer has (kernel §3.2).
- The API only. The frontend is plan 4's; "After this plan" records what it must do.

**Architecture:**
- **Kernel** (`hennery-kernel`):
  - `schema.rs`: migration 5, the `passkeys` table, with `owner_id` from its first migration.
  - `passkeys.rs` (new):
    - `relying_party(&PublicUrl)`, the WebAuthn relying party;
    - `Ceremonies`, the store of ceremonies under way;
    - the operator's passkey methods: register, list, remove, log in, step up.

    It joins the owner-filter audit's `SOURCES`.
  - `operator.rs`:
    - `PublicUrl::rp_id()`;
    - the `ceremonies` and `passkey_limiter` fields;
    - `reset_public_url` removes the passkeys of a host name `public_url` no longer has, and ends every ceremony.
  - `auth_api.rs`: eight routes under `/api/auth/passkeys/…` and `/api/auth/step-up/passkey/…`, behind the existing browser rules, cookie and step-up layers.
  - `ratelimit.rs`: `Policy::PASSKEY_LOGIN`.
  - `admin.rs`: `PublicUrlReset` reports `passkeys_removed`.
- **Wire** (`hennery-proto`): `PasskeyRegisterRequest`, `PasskeyCeremony`, `PasskeyFinishRequest`, `PasskeyItem`. The schema and TypeScript files are regenerated.
- **CLI** (`hennery`): `admin reset-public-url` warns about passkeys before it asks, and reports how many it removed.
- **Tests:** a software passkey (`webauthn-authenticator-rs`'s `SoftPasskey`) stands in for the browser and its authenticator, at the kernel level (`crates/hennery-kernel/tests/passkeys.rs`) and over HTTP (`crates/hennery-testkit/tests/passkeys.rs`).

**Tech Stack:** Rust (edition 2024, MSRV 1.88), rusqlite 0.40 (bundled SQLite 3.53.2), tokio, axum 0.8. New crates:
- `webauthn-rs = "=0.5.5"`, default features off, for the kernel;
- `webauthn-authenticator-rs = "=0.5.5"` with `softpasskey`, a dev-dependency of the kernel and the testkit.

`webauthn-rs-core` links OpenSSL (`openssl` 0.10.81, `openssl-sys` 0.9.117). `flake.nix`'s dev shell gains `openssl` and `pkg-config` (Task 1). `Cargo.lock` changes in Tasks 1 and 5, each by one `cargo build --workspace` without `--locked`; every other command runs `--locked`.

## Decisions this plan makes where the spec is silent

Each gives the choice, the alternatives, and the cost if it is wrong, so a reviewer can confirm it on its own. Items marked **(amendment)** depart from explicit spec text and should be written back into it. None has been reviewed yet.

1. **The relying party is `public_url`'s host and origin, exactly.**
   - **Choice:** `relying_party(&PublicUrl)` builds `webauthn-rs`'s `Webauthn` with:
     - the RP id: `public_url`'s host, lowercase, as the `url` crate gives it (`Url::domain`);
     - the origin: `public_url`'s origin, the only one accepted;
     - `allow_subdomains(false)` and `allow_any_port(false)` (kernel §3.2);
     - the RP name `hennery`, and a timeout of `CEREMONY_TTL_SECS` (decision 5).

     It is built at every start and finish from the cached `public_url`, so a reset takes effect at once (it is a small struct; nothing is cached).
   - **An IP address has no RP id.** WebAuthn binds a credential to a domain: browsers refuse an IP address as an RP id, and so does `WebauthnBuilder`. With `public_url` at `http://127.0.0.1:…` or `http://[::1]:…`, every passkey start answers 409 `passkeys_unavailable`, and the password works as before. `hennery up`'s default setup link is `http://localhost:PORT`, which has one.
   - **Alternatives:**
     - **The registrable parent domain** (`example.com` for `hennery.example.com`), so passkeys survive a move between subdomains. The spec forbids subdomains, and every sibling subdomain could then ask for the owner's passkeys.
     - **Any port** (`allow_any_port(true)`), so a port move keeps the origin. The spec forbids it, and any other service on the host could run a ceremony.
   - **Cost if wrong:** the RP id is bound into every credential. A different rule later strands every passkey registered under this one.
2. **Passkeys add to the password; they never replace it.** This answers 3b-iii's O9 question.
   - **Choice:**
     - Setup still sets a password (kernel §3.1), and no route removes it. So the "at least one other login method" of kernel §3.2 always remains, and every passkey is removable.
     - No passkey-only owner exists in 3c. `reset_password`'s exactly-one-row check (3b-iii decision 8) stays as it is, still unreachable.
     - A password reset leaves the passkeys as they are (`a_password_reset_keeps_the_passkeys`). See question 1.
   - The umbrella's "passkeys as the primary path" (§7.3) is the frontend's to honour: offer the passkey first, keep the password behind it.
   - **Alternatives:** **passkey-only owners** (remove the password once a passkey exists). That needs:
     - a route that removes the password;
     - the "one method remains" check across two tables, in one transaction with each removal;
     - `reset_password` inserting a password row where there is none: the admin socket's recovery;
     - step-up by password unavailable to such an owner.

     All of that is more surface for a v1 whose recovery is the admin socket's password reset.
   - **Cost if wrong:** a later plan adds `DELETE /api/auth/password` with that check, and makes `reset_password` insert. The tables stay as they are.
3. **The `passkeys` table (amendment to kernel §1.1).**
   - **Choice:** kernel migration 5:

     ```sql
     passkeys(id TEXT PK, owner_id TEXT NOT NULL REFERENCES owners(id),
       credential_id TEXT NOT NULL UNIQUE, credential TEXT NOT NULL,
       sign_count INTEGER NOT NULL, label TEXT NOT NULL,
       created_at INTEGER NOT NULL, last_used_at INTEGER)
     ```

     - `id`: `passkey-` and 16 random hex digits, as the API names it.
     - `credential`: `webauthn-rs`'s `Passkey`, as its own `Serialize` writes it.
     - `credential_id`: the credential id in lowercase hex. **Unique across owners**, because `webauthn-rs` requires it ("You MUST assert that the registered `CredentialID` has not previously been registered to any other account"). A registration that clashes answers 409 `already_registered` and writes nothing (`a_credential_registered_already_is_refused`).
     - `sign_count`: the counter last accepted, beside the JSON. `Passkey` hides its counter without the `danger-credential-internals` feature, and a column lets a login compare and set it in one statement (decision 6).
     - `label`: 1 to 64 characters after trimming, with no control characters.
     - The list is ordered by `created_at`, then `rowid`: the order of registration.
   - **Every statement names the owner.** `passkeys.rs` holds SQL, so the audit's A3 fails until it is in `SOURCES`. Task 3's Step 2 shows that failure. It ends with 9 statements; `operator.rs` ends with 20.
   - **The user handle is derived, not stored:** the first 16 bytes of the SHA-256 of the owner's id, as a UUID. An authenticator stores it with the credential. It names no one, and is the same at every registration. Nothing reads it back: logins list the owner's credentials (decision 8).
   - **Alternatives:**
     - `credential_id` unique per owner, `UNIQUE(owner_id, credential_id)`, as 3b-iii decision 7 suggests for host keys under teams. Here it would let one credential sign in to two accounts; `webauthn-rs` forbids it. The cost is the same existence oracle as decision 7's: for teams, a 409 tells a caller that some other owner holds a credential. Recorded in "After this plan".
     - A stored, random user handle (a column on `owners`). That is a migration of `owners` for no gain with one owner.
   - **Cost if wrong:** a later migration of a table that is small and has no references.
4. **No attestation.**
   - **Choice:** `start_passkey_registration` asks for no attestation (`webauthn-rs` fixes it so for passkeys), and accepts any authenticator. Default features are off; `attestation`, the only default, gates the attested APIs not used here.
   - The registration's answer stays small: 774 bytes from the software passkey, since browsers strip attestation statements when none is asked for. The auth routes' 16 KiB body limit (`MAX_BODY_BYTES`) holds for passkeys too (`a_finish_larger_than_the_body_limit_is_refused`).
   - **Alternatives:** attested passkeys against an authenticator CA list (`start_attested_passkey_registration`). They refuse synced passkeys, which carry no attestation (iCloud Keychain, Google Password Manager), and the vendor list needs upkeep. A self-hosted tool with one owner gains nothing from knowing the authenticator's make.
   - **Cost if wrong:** requiring attestation later means registering every passkey again.
5. **Ceremony state lives in memory: single use, five minutes, bound to its session (kernel §3.2).**
   - **Choice:** `Operator::ceremonies`, a `Ceremonies`:
     - **Keys:** a random 256-bit id (64 hex characters), handed to the browser with the options.
     - **Kinds:** `Register { session_id, label }`, `Login`, `StepUp { session_id }`, each with `webauthn-rs`'s state.
     - **Single use:** `take` removes the ceremony, whatever the finish then finds. A finish with the wrong session or the wrong kind uses it up, and so does one that does not verify.
     - **TTL:** `CEREMONY_TTL_SECS` (300 s), checked against the caller's `now`. `webauthn-rs` checks no time itself: its timeout is a hint to the browser, given the same 300 s.
     - **One per session per kind:** a session has at most one registration and one step-up under way. A new start replaces the old.
     - **A cap:** at most `MAX_CEREMONIES` (1024) live. Expired ones go first, then the oldest.
     - **A move of `public_url` ends them all** (decision 9).
   - **Why memory is enough:** one collector serves a data directory (3b-ii decision 6), and a ceremony lasts minutes. A restart drops them; the browser starts again.
   - **Alternatives:**
     - **A table:** it needs `danger-allow-state-serialisation`, a write per start, and a sweep, to survive restarts no one needs.
     - **State in a signed cookie:** `webauthn-rs` warns that the state must stay on the server ("YOU MUST STORE THE `PasskeyRegistration` VALUE SERVER SIDE"), or a challenge can be replayed.
   - **Cost if wrong:** a flood of login starts from more addresses than the limiter tracks (decision 8) can push the owner's ceremony out. Passkey login fails while it lasts; the password is not affected. Recorded.
6. **The counter must move on, and a passkey whose counter does not is refused.**
   - **Choice:** `counter_moves_on(stored, sent)`: the sent counter must exceed the one stored, unless both are 0. Synced passkeys always send 0. A cloned authenticator sends a counter its original has already passed.
     - `webauthn-rs` checks the counter against the snapshot in the ceremony, taken at its start.
     - hennery checks it again against `sign_count`, inside the finish's transaction. The `UPDATE` sets it only `WHERE sign_count = ?` (the value just read). Two ceremonies begun before either finishes cannot both pass with one counter.
   - **On a counter that does not move on:** 401 `passkey_refused`. Nothing is written, and a warning names the passkey. The passkey is not disabled or removed.
   - **A new passkey's `sign_count` is 0**, below whatever its authenticator sends next. A registration's own counter sits in the `Passkey` JSON, out of reach. A real authenticator whose registration counter was N sends more than N. A clone's counter at or below N is still refused before the first genuine login: `webauthn-rs` compares it with the snapshot, whose counter is N.
   - **Alternatives:**
     - **Disable the passkey** on a regression: a flag, and a way to re-enable it.
     - **Remove it:** whoever holds the clone could remove the owner's passkey at will.
     - **Trust `webauthn-rs`'s snapshot check alone:** two ceremonies begun together would both pass.
   - **Cost if wrong:** a passkey with a live clone stays registered. The clone signs in whenever its counter is ahead; the owner sees `last_used_at` and can remove the passkey. See question 5.
7. **Only a stepped-up session registers or removes a passkey (amendment to kernel §3.4).**
   - **Choice:** `register/start`, `register/finish` and `DELETE /api/auth/passkeys/{id}` sit behind `require_operator` and `require_step_up`: a password or passkey check within five minutes. The registration is bound to the session that began it (decision 5).
     - Setup's session starts stepped up, so "setup then offers passkey registration" (kernel §3.1) works for five minutes without a second password (`a_passkey_registered_at_setup_signs_in_steps_up_and_is_removed`).
     - The finish is checked too. A registration begun at 4:59 into the window is refused at its finish: 403 `step_up_required`. The ceremony is still live then, so the frontend steps up and retries the same finish.
   - Kernel §3.4 lists "revoking … passkeys", not adding them. Adding one is at least as sensitive: a stolen cookie would gain a lasting login method. That is the amendment.
   - **Alternatives:** registration from any signed-in session. One prompt fewer, and a stolen cookie becomes a passkey.
   - **Cost if wrong:** one more step-up prompt.
8. **Login and step-up by passkey.**
   - **Login** (browser rules only: `Origin`, JSON; no cookie):
     - `start` lists every passkey of the owner's in `allowCredentials`. It answers 409 `no_passkeys` when there is none, and `passkeys_unavailable` without an RP id.
     - `finish` verifies the answer. `webauthn-rs`'s passkeys require user verification. Then, in one transaction:
       - the counter is compared and set (decision 6);
       - the session is opened, only while the passkey is still the owner's.

       The ceremony's snapshot would verify a passkey removed since its start; the transaction refuses it, 401 `passkey_refused` (`a_passkey_removed_during_its_ceremony_is_refused`).
     - The session starts stepped up, as a password login's does (3b-i), and gets the same cookie.
   - **A budget of its own:** `Operator::passkey_limiter`, `Policy::PASSKEY_LOGIN`.
     - It allows 30 starts a minute per client address, then the same exponential lockout as the password's. Every start counts until a finish succeeds.
     - It is not the password's budget: a password lockout does not stop passkey login, and passkey starts take nothing from the password's (3b-i's obligation; `passkey_login_has_a_budget_of_its_own`).
     - Why 30 and not 5: a login page that offers passkeys starts a ceremony each time it loads.
   - **Step-up** (signed in): the ceremony is bound to the session. The finish sets the counter and `last_step_up_at` in one transaction, or answers 401 `unauthenticated` when the session ended meanwhile. No limiter: it needs a session, and each session has at most one step-up ceremony.
   - **Alternatives:**
     - **Discoverable, "usernameless" login with autofill** (`conditional-ui`, a preview feature of `webauthn-rs`): smoother in the browser, but it needs resident keys and a preview API. With one owner there is no one to pick.
     - **The password's limiter** for passkeys too: it breaks 3b-i's obligation.
     - **No limiter:** memory stays bounded by the cap, but one address could push out everyone's ceremonies.
   - **What an unauthenticated caller learns:** whether the owner has a passkey (`no_passkeys`), and its credential ids (`allowCredentials`), as in any username-first WebAuthn login. See question 3.
   - **Cost if wrong:** a lockout policy is one constant. A discoverable flow is a later addition beside this one.
9. **`reset-public-url` removes the passkeys of a host name it no longer has (amendment to kernel §3.2).**
   - **Choice:** `reset_public_url` compares the old RP id with the new one, inside its transaction.
     - **The host name changes** (another domain, or an IP address): every passkey is removed, as kernel §3.2's "existing passkeys stop working" implies.
     - **Another port or scheme:** the RP id stays, so the passkeys stay, and sign in at the new origin, not at the old (`moving_public_url_to_another_port_keeps_the_passkeys`). That is the amendment.
     - **Every ceremony under way ends,** either way.
   - **What the operator sees:**
     - `Reset::Done` and `AdminResponse::PublicUrlReset` carry `passkeys_removed`.
     - `hennery admin reset-public-url` says "Passkeys stop working if the host name changes, and are then removed." in its confirmation, before anything is sent. It reports the count afterwards.
   - **Why remove them rather than keep them:** a real authenticator scopes a credential by RP id, so after a host move the browser offers none of them. Kept, they would be listed as if usable, and sent in `allowCredentials` for nothing.
     - The software passkey signs for whatever RP id it is asked, so it would still sign in after a host move. What stops a real one is the authenticator, not the server's check (found in the spike, recorded under "Not tested here").
   - **Alternatives:**
     - **Remove them on every reset,** as the spec's text reads: one condition fewer, and a port move costs every passkey.
     - **Keep them all:** dead passkeys stay listed.
   - **The future `PATCH /api/settings`** (step-up, kernel §3.4) must do the same. Recorded.
   - **Cost if wrong:** one comparison.
10. **`webauthn-rs` 0.5.5, and `webauthn-authenticator-rs`'s software passkey for tests (amendment to kernel §11).**
    - **`webauthn-rs = "=0.5.5"`** (2026-04-30; MSRV 1.88, the workspace's), with default features off. The 0.6 line is pre-release (`0.6.1-dev`).
    - **No features, and why each is left off:**
      - `danger-allow-state-serialisation`: the state stays on the server, in memory (decision 5);
      - `danger-credential-internals`: the counter is kept in a column (decision 3);
      - `conditional-ui`: a preview (decision 8);
      - `resident-key-support`: no discoverable credentials;
      - `danger-user-presence-only-security-keys`: user verification stays required.
    - **OpenSSL:** `webauthn-rs-core` links it.
      - The dev shell gains `openssl` and `pkg-config` (Task 1).
      - CI (`.github/workflows/ci.yml`) installs neither. The runner images have them: `ubuntu-latest` ships `libssl-dev` and `pkg-config`, and `macos-latest` ships Homebrew's `openssl@3`, which `openssl-sys` looks for. Only macOS, through nix, could be built here, so CI's first run is their proof. If a runner lacks them, add `sudo apt-get install -y libssl-dev pkg-config` or `brew install openssl@3` to the workflow, not to anyone's machine.
      - A release binary linking OpenSSL statically (musl) is plan 7's.
    - **The software passkey:** `webauthn-authenticator-rs = "=0.5.5"` with `softpasskey`, a dev-dependency of the kernel and the testkit.
      - It comes from the same project, and speaks the same `webauthn-rs-proto` types. `SoftPasskey::new(true)` claims user verification.
      - Its tree adds no USB, NFC or Bluetooth crate: `cargo tree --target x86_64-unknown-linux-gnu` was checked, so no `libudev`, `pcsclite` or `dbus` is needed on `ubuntu-latest`.
    - **Kernel §11 named the `passkey` crate** (1Password's, 0.5). Not taken:
      - its types are not `webauthn-rs`'s, so every test would convert JSON;
      - it validates origins against a public-suffix list of its own.
    - **Alternatives:** assertions built by hand with `p256`. That is a test seam we would have to trust as much as the code under test.

//! Passkeys (kernel spec §3.2, plan 3c): WebAuthn with `webauthn-rs`.
//!
//! - **The relying party is `public_url`** (decision 1): its host is the RP
//!   id and its origin the one origin accepted, with no subdomain and no
//!   other port. A `public_url` whose host is an IP address has no RP id,
//!   so passkeys are unavailable there.
//! - **The user handle is derived from the owner's id** (decision 3), not
//!   stored: an authenticator keeps it, and it names no one.

use crate::operator::PublicUrl;
use sha2::{Digest, Sha256};
use webauthn_rs::prelude::{Url, Uuid, Webauthn, WebauthnBuilder};

/// How long a ceremony may take from its start to its finish, and the
/// timeout the browser is given (decision 5).
pub const CEREMONY_TTL_SECS: i64 = 5 * 60;

/// The relying party's name, which an authenticator may show.
const RP_NAME: &str = "hennery";

/// The relying party for `public_url`: `None` when its host is an IP
/// address (decision 1).
pub fn relying_party(public_url: &PublicUrl) -> Option<Webauthn> {
    let rp_id = public_url.rp_id()?;
    let origin = Url::parse(public_url.origin()).ok()?;
    WebauthnBuilder::new(rp_id, &origin)
        .ok()?
        .rp_name(RP_NAME)
        .allow_subdomains(false)
        .allow_any_port(false)
        .timeout(std::time::Duration::from_secs(CEREMONY_TTL_SECS as u64))
        .build()
        .ok()
}

/// The owner's WebAuthn user handle: the first 16 bytes of the SHA-256 of
/// their id. The same owner always gets the same handle.
pub fn user_handle(owner_id: &str) -> Uuid {
    let digest = Sha256::digest(owner_id.as_bytes());
    let mut bytes = [0u8; 16];
    bytes.copy_from_slice(&digest[..16]);
    Uuid::from_bytes(bytes)
}

pub const CEREMONY_TTL_SECS: i64 = 5 * 60;

/// The relying party's name, which an authenticator may show.
const RP_NAME: &str = "hennery";

/// The relying party for `public_url`: `None` when its host is an IP
/// address (decision 1).
pub fn relying_party(public_url: &PublicUrl) -> Option<Webauthn> {
    let rp_id = public_url.rp_id()?;
    let origin = Url::parse(public_url.origin()).ok()?;
    WebauthnBuilder::new(rp_id, &origin)
        .ok()?
        .rp_name(RP_NAME)
        .allow_subdomains(false)
        .allow_any_port(false)
        .timeout(std::time::Duration::from_secs(CEREMONY_TTL_SECS as u64))
        .build()
        .ok()
}

/// The owner's WebAuthn user handle: the first 16 bytes of the SHA-256 of
/// their id. The same owner always gets the same handle.
pub fn user_handle(owner_id: &str) -> Uuid {
    let digest = Sha256::digest(owner_id.as_bytes());
    let mut bytes = [0u8; 16];
    bytes.copy_from_slice(&digest[..16]);
    Uuid::from_bytes(bytes)
}

/// A ceremony begun and not yet finished: what it is for, and the state
/// `webauthn-rs` checks its finish against.
pub enum Ceremony {
    /// Registering a passkey, labelled `label`, from a signed-in session.
    Register {
        session_id: String,
        label: String,
        state: PasskeyRegistration,
    },
    /// Signing in.
    Login { state: PasskeyAuthentication },
    /// Stepping up a signed-in session.
    StepUp {
        session_id: String,
        state: PasskeyAuthentication,
    },
}

impl Ceremony {
    /// The session a registration or a step-up belongs to, and its kind:
    /// a session has at most one live ceremony of each.
    fn slot(&self) -> Option<(&str, u8)> {
        match self {
            Self::Register { session_id, .. } => Some((session_id, 0)),
            Self::StepUp { session_id, .. } => Some((session_id, 1)),
            Self::Login { .. } => None,
        }
    }
}

struct Live {
    ceremony: Ceremony,
    expires_at: i64,
    /// The order ceremonies began in: past capacity, the oldest goes.
    seq: u64,
}

#[derive(Default)]
struct Table {
    live: HashMap<String, Live>,
    seq: u64,
}

/// The live ceremonies (decision 5).
pub struct Ceremonies {
    capacity: usize,
    table: Mutex<Table>,
}

impl Default for Ceremonies {
    fn default() -> Self {
        Self::with_capacity(MAX_CEREMONIES)
    }
}

impl Ceremonies {
    pub fn with_capacity(capacity: usize) -> Self {
        Self {
            capacity,
            table: Mutex::new(Table::default()),
        }
    }

    fn table(&self) -> std::sync::MutexGuard<'_, Table> {
        self.table.lock().expect("ceremonies lock")
    }

    /// Begin `ceremony` and return its id (64 hex characters). Expired
    /// ceremonies are dropped first, and the session's earlier ceremony of
    /// the same kind; past capacity, the oldest live one goes too.
    pub fn begin(&self, ceremony: Ceremony, now: i64) -> String {
        let id = hex::encode(random_bytes::<32>());
        let mut table = self.table();
        table.live.retain(|_, live| live.expires_at > now);
        if let Some(slot) = ceremony.slot() {
            table.live.retain(|_, live| live.ceremony.slot() != Some(slot));
        }
        while table.live.len() >= self.capacity.max(1) {
            let Some(oldest) = table
                .live
                .iter()
                .min_by_key(|(_, live)| live.seq)
                .map(|(id, _)| id.clone())
            else {
                break;
            };
            table.live.remove(&oldest);
        }
        table.seq += 1;
        let seq = table.seq;
        table.live.insert(
            id.clone(),
            Live {
                ceremony,
                expires_at: now + CEREMONY_TTL_SECS,
                seq,
            },
        );
        id
    }

    /// Take the ceremony `id` names: it is gone whatever its finish then
    /// finds. `None` when there is none, or it has expired.
    pub fn take(&self, id: &str, now: i64) -> Option<Ceremony> {
        let live = self.table().live.remove(id)?;
        (live.expires_at > now).then_some(live.ceremony)
    }

    /// Drop every ceremony (`public_url` moved: decision 9).
    pub fn clear(&self) {
        self.table().live.clear();
    }

    /// How many are live, expired ones included until the next `begin`.
    pub fn len(&self) -> usize {
        self.table().live.len()
    }

    pub fn is_empty(&self) -> bool {
        self.len() == 0
    }
}

    /// with the browser's `credential` (`RegisterPublicKeyCredential` as

            label,
            state,

        else {

            return Ok(Err(Refused::Unavailable));
        };
        let credential: RegisterPublicKeyCredential = match serde_json::from_value(credential.clone()) {
            Ok(credential) => credential,

    /// record it on the session, in one transaction with the passkey's
    /// counter. `Ok(false)` when the session has ended meanwhile.
    pub fn finish_passkey_step_up(
        &self,

        ceremony_id: &str,
        credential: &serde_json::Value,
        now: i64,
    ) -> Result<std::result::Result<bool, Refused>> {
        let Some(Ceremony::StepUp {
            session_id: begun_by,
            state,
        }) = self.ceremonies.take(ceremony_id, now)
        else {

            return Ok(Ok(false));
        }
        tx.commit()?;
        Ok(Ok(true))
    }

/// Move the counter of the passkey `result` names on, and mark it used at
/// `now`, in `tx` (decision 6). Refused, changing nothing, when the owner
/// has no such passkey (removed since the ceremony began) or its counter
/// did not move on. The counter is compared and set in one statement.
fn record_use(
    tx: &rusqlite::Transaction<'_>,
    owner: &str,
    result: &AuthenticationResult,
    now: i64,
) -> Result<std::result::Result<(), Refused>> {
    let stored: Option<(String, String, i64)> = tx
        .query_row(
            "SELECT id, credential, sign_count FROM passkeys WHERE credential_id = ?1 AND owner_id = ?2",
            params![stored_id(result.cred_id().as_ref()), owner],
            |r| Ok((r.get(0)?, r.get(1)?, r.get(2)?)),
        )
        .optional()?;
    let Some((id, credential, sign_count)) = stored else {
        return Ok(Err(Refused::Passkey));
    };
    if !counter_moves_on(sign_count as u32, result.counter()) {
        tracing::warn!(
            passkey = %id,
            stored = sign_count,
            sent = result.counter(),
            "a passkey's counter did not move on, so it may have been cloned: refused"
        );
        return Ok(Err(Refused::Passkey));
    }
    let mut passkey: Passkey = serde_json::from_str(&credential)?;
    passkey.update_credential(result);
    let updated = tx.execute(
        "UPDATE passkeys SET credential = ?1, sign_count = ?2, last_used_at = ?3
         WHERE id = ?4 AND owner_id = ?5 AND sign_count = ?6",
        params![
            serde_json::to_string(&passkey)?,
            result.counter(),
            now,
            id,
            owner,
            sign_count
        ],
    )?;
    if updated != 1 {
        return Ok(Err(Refused::Passkey));
    }
    Ok(Ok(()))
}

        path: &str,

    ) -> Result<PasskeyCeremony, (u16, String)> {
        let mut req = self.post(session, path);
        if let Some(body) = body {
            req = req.json(&body);
        }
        let resp = req.send().await.unwrap();
        if resp.status() == 200 {
            Ok(resp.json().await.unwrap())
        } else {
            Err(code_of(resp).await)
        }
    }

    async fn finish(
        &self,
        session: Option<&str>,
        path: &str,
        ceremony_id: &str,
        credential: serde_json::Value,
    ) -> reqwest::Response {
        self.post(session, path)
            .json(&PasskeyFinishRequest {
                ceremony_id: ceremony_id.into(),
                credential,
            })
            .send()
            .await
            .unwrap()
    }

    /// Register a passkey labelled `label` from `session` (stepped up).
    async fn register(&self, session: &str, passkey: &mut Passkey, label: &str) -> PasskeyItem {
        let ceremony = self
            .start_ceremony(
                Some(session),
                "/api/auth/passkeys/register/start",
                Some(serde_json::to_value(PasskeyRegisterRequest { label: label.into() }).unwrap()),
            )
            .await
            .expect("the registration began");
        let options: CreationChallengeResponse = serde_json::from_value(ceremony.options).unwrap();
        let credential = passkey
            .do_registration(Url::parse(PUBLIC_URL).unwrap(), options)
            .unwrap();
        let resp = self
            .finish(
                Some(session),
                "/api/auth/passkeys/register/finish",
                &ceremony.ceremony_id,
                serde_json::to_value(credential).unwrap(),
            )
            .await;
        assert_eq!(resp.status(), 201);
        resp.json().await.unwrap()
    }

    /// Begin a login, and the passkey's answer made at `origin`.
    async fn begin_login(&self, passkey: &mut Passkey, origin: &str) -> (String, serde_json::Value) {
        let ceremony = self
            .start_ceremony(None, "/api/auth/passkeys/login/start", None)
            .await
            .expect("the login began");
        (ceremony.ceremony_id, answer(passkey, origin, ceremony.options))
    }

    /// Sign in with `passkey`: the response to the finish.
    async fn passkey_login(&self, passkey: &mut Passkey) -> reqwest::Response {
        let (ceremony_id, assertion) = self.begin_login(passkey, PUBLIC_URL).await;
        self.finish(None, "/api/auth/passkeys/login/finish", &ceremony_id, assertion)
            .await
    }

    /// Step `session` up with `passkey`: the response to the finish.
    async fn passkey_step_up(&self, session: &str, passkey: &mut Passkey) -> reqwest::Response {
        let ceremony = self
            .start_ceremony(Some(session), "/api/auth/step-up/passkey/start", None)
            .await
            .expect("the step-up began");
        let assertion = answer(passkey, PUBLIC_URL, ceremony.options);
        self.finish(
            Some(session),
            "/api/auth/step-up/passkey/finish",
            &ceremony.ceremony_id,
            assertion,
        )
        .await
    }

    async fn password_login(&self, password: &str) -> reqwest::Response {
        self.post(None, "/api/auth/login")
            .json(&serde_json::json!({ "password": password }))
            .send()
            .await
            .unwrap()
    }

    async fn list(&self, session: &str) -> reqwest::Response {
        self.request(Some(session), "GET", "/api/auth/passkeys")
            .send()
            .await
            .unwrap()
    }
}

/// The passkey's answer to a login or step-up's `options`, made at
/// `origin`.
fn answer(passkey: &mut Passkey, origin: &str, options: serde_json::Value) -> serde_json::Value {
    let options: RequestChallengeResponse = serde_json::from_value(options).unwrap();
    let assertion = passkey.do_authentication(Url::parse(origin).unwrap(), options).unwrap();
    serde_json::to_value(assertion).unwrap()
}

async fn code_of(resp: reqwest::Response) -> (u16, String) {
    let status = resp.status().as_u16();
    (
        status,
        resp.json::<ApiError>().await.map(|e| e.code).unwrap_or_default(),
    )
}

/// The session token a response's `Set-Cookie` carries.
fn session_token(resp: &reqwest::Response) -> String {
    let cookie = resp.headers()["set-cookie"].to_str().unwrap();
    cookie
        .strip_prefix("hennery_session=")
        .unwrap()
        .split(';')
        .next()
        .unwrap()
        .to_string()
}

    let resp = c
        .post(None, "/api/auth/passkeys/login/finish")
        .header("content-type", "text/plain")
        .body("{}")
        .send()
        .await
        .unwrap();
    assert_eq!(code_of(resp).await, (415, "unsupported_media_type".into()));

    for path in [
        "/api/auth/passkeys/register/start",
        "/api/auth/passkeys/register/finish",
        "/api/auth/step-up/passkey/start",
        "/api/auth/step-up/passkey/finish",
    ] {

        let resp = reqwest::Client::new()

            .header("cookie", format!("hennery_session={session}"))
            .json(&serde_json::json!({}))
            .send()
            .await
            .unwrap();
        assert_eq!(code_of(resp).await, (403, "origin_mismatch".into()), "{path}");
    }
    let resp = c.request(None, "GET", "/api/auth/passkeys").send().await.unwrap();
    assert_eq!(code_of(resp).await, (401, "unauthenticated".into()));
    let resp = c
        .request(Some(&session), "GET", "/api/auth/passkeys")
        .header("sec-fetch-site", "cross-site")
        .send()
        .await
        .unwrap();
    assert_eq!(code_of(resp).await, (403, "cross_site".into()));
}

        ),
        Refused::AlreadyRegistered => error(
            StatusCode::CONFLICT,
            "already_registered",
            "this passkey is registered already",
        ),
        Refused::Unavailable => passkeys_unavailable(),
    }
}

fn passkey_item(record: PasskeyRecord) -> PasskeyItem {
    PasskeyItem {
        id: record.id,
        label: record.label,
        created_at: rfc3339(record.created_at),
        last_used_at: record.last_used_at.map(rfc3339),
    }
}

/// `POST /api/auth/passkeys/login/start`: a login ceremony over the
/// owner's passkeys. Every start counts against the client's address on
/// the passkey budget until a login succeeds (plan 3c decision 8).
async fn passkey_login_start(
    State(operator): State<Arc<Operator>>,
    ConnectInfo(peer): ConnectInfo<SocketAddr>,
) -> Response {
    if let Err(retry_after) = operator.passkey_limiter.attempt(peer.ip(), Instant::now()) {
        return rate_limited(
            retry_after,
            "too many passkey logins begun from this address; try again later",
        );
    }
    started(operator.start_passkey_login(unix_now()))
}

/// `POST /api/auth/passkeys/login/finish`: 204 and a new session cookie,
/// the session stepped up, as a password login's is.
async fn passkey_login_finish(
    State(operator): State<Arc<Operator>>,
    ConnectInfo(peer): ConnectInfo<SocketAddr>,
    headers: HeaderMap,
    Json(req): Json<PasskeyFinishRequest>,
) -> Response {
    match operator.finish_passkey_login(&req.ceremony_id, &req.credential, &user_agent(&headers), unix_now()) {
        Ok(Ok(token)) => {
            operator.passkey_limiter.succeeded(peer.ip());
            with_cookie(
                StatusCode::NO_CONTENT.into_response(),
                &session_cookie(&token, secure_cookies(&operator)),
            )
        }
        Ok(Err(why)) => refused(why),
        Err(err) => internal(err),
    }
}

/// `POST /api/auth/step-up/passkey/start`: a step-up ceremony for the
/// request's session (kernel spec §3.4).
async fn passkey_step_up_start(
    State(operator): State<Arc<Operator>>,
    Extension(session): Extension<Authenticated>,
) -> Response {
    started(operator.start_passkey_step_up(&session.session_id, unix_now()))
}

/// `POST /api/auth/step-up/passkey/finish`: 204, the session stepped up
/// for five minutes.
async fn passkey_step_up_finish(
    State(operator): State<Arc<Operator>>,
    Extension(session): Extension<Authenticated>,
    Json(req): Json<PasskeyFinishRequest>,
) -> Response {
    match operator.finish_passkey_step_up(&session.session_id, &req.ceremony_id, &req.credential, unix_now()) {
        Ok(Ok(true)) => StatusCode::NO_CONTENT.into_response(),
        Ok(Ok(false)) => error(StatusCode::UNAUTHORIZED, "unauthenticated", "sign in first"),
        Ok(Err(why)) => refused(why),
        Err(err) => internal(err),
    }
}

/// `GET /api/auth/passkeys`: the owner's passkeys, oldest first.
async fn list_passkeys(State(operator): State<Arc<Operator>>) -> Response {
    match operator.passkeys() {
        Ok(records) => Json(records.into_iter().map(passkey_item).collect::<Vec<_>>()).into_response(),
        Err(err) => internal(err),
    }
}

/// `DELETE /api/auth/passkeys/{id}` (step-up): 204, or 404 if there is no
/// such passkey. The password stays (plan 3c decision 2).
async fn remove_passkey(State(operator): State<Arc<Operator>>, Path(id): Path<String>) -> Response {
    match operator.remove_passkey(&id) {
        Ok(true) => StatusCode::NO_CONTENT.into_response(),
        Ok(false) => error(StatusCode::NOT_FOUND, "not_found", "no such passkey"),
        Err(err) => internal(err),
    }
}

/// `POST /api/auth/passkeys/register/start` (step-up, plan 3c decision 7):

async fn passkey_register_start(
    State(operator): State<Arc<Operator>>,
    Extension(session): Extension<Authenticated>,
    Json(req): Json<PasskeyRegisterRequest>,

## After this plan

**What the frontend must do (plan 4):**
- **Setup:** right after `POST /api/setup`'s 201, offer a passkey. `register/start` with a label, then `navigator.credentials.create`, then `register/finish`, all within five minutes of setup, while its session is stepped up.
- **The ceremonies:**
  - pass `options.publicKey` through `PublicKeyCredential.parseCreationOptionsFromJSON` (registration) or `parseRequestOptionsFromJSON` (login, step-up);
  - send `credential.toJSON()` as the finish's `credential`;
  - browsers without those methods need the base64url fields decoded and encoded by hand.
  - A cancelled prompt (`NotAllowedError`) needs no call: the ceremony expires.
- **Login:** offer the passkey first (umbrella §7.3), the password behind it. Hide the passkey button on 409 `no_passkeys` or `passkeys_unavailable`; no endpoint says beforehand whether there is one. On 429 honour `Retry-After`.
- **Step-up:** on 403 `step_up_required`, offer the passkey (`step-up/passkey/start`) and the password, then retry the refused request. A registration's finish refused this way can be retried as it was: the step-up layer refuses before the ceremony is taken.
- **Settings:** list the passkeys (label, created, last used), and remove one (step-up). Warn before a `public_url` change that passkeys stop working if the host name changes (kernel §3.2).
- **The answers:** 400 `invalid_ceremony` means start again. 401 `passkey_refused` means the passkey was not accepted. 409 `already_registered` means this authenticator holds a passkey already.

**Questions for the security review,** most important first:
1. **Recovery leaves every passkey.** `hennery admin reset-password` ends every session but keeps the passkeys, and no admin command lists or removes them. A passkey added with a stolen, stepped-up session survives the recovery. Should `reset-password` remove the passkeys too, or should `hennery admin` gain `passkeys` and `remove-passkey`?
2. **A port move keeps the passkeys** (decision 9). That is an amendment to kernel §3.2's "existing passkeys stop working". Keep it, or remove them on every move?
3. **What an unauthenticated caller learns:** whether the owner has a passkey (`no_passkeys`), and its credential ids (`allowCredentials`). Is that acceptable for a single-owner install, or should the login start answer alike either way?
4. **Ceremonies pushed out by a flood** from many addresses (decision 5). Passkey login fails while it lasts; the password does not. Is the cap with eviction enough, or should login ceremonies have a cap of their own?
5. **A counter that goes back** is refused, not acted on (decision 6). Should the passkey be disabled until the owner confirms it?
6. **Removing a passkey ends no session.** Sessions are not tied to the method that opened them. Should removing a passkey end the sessions it opened, which would need a column on `auth_sessions`?
7. **Step-up at registration's finish too** (decision 7): a registration begun late in the window needs a second step-up. Is the check at the start enough?
